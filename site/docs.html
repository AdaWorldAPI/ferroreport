Documentation

ferroreport takes a JasperReports template (.jrxml), your rows as JSON and your parameters, and returns a PDF, an Excel workbook or a CSV file. Every way of calling it, from the command line to Python, uses the same engine and produces the same bytes.

Your first PDF

You need three files: the template you designed in Jaspersoft Studio, the rows, and the parameters.

ferroreport render invoice.jrxml --data rows.json --params params.json -o invoice.pdf
# rows.json: one object per detail row; keys are the template's <field> names
[
  { "sku": "FX-1000", "description": "Hydraulic pump 2HP", "qty": 21, "price": "185.00" },
  { "sku": "FX-1007", "description": "Stainless steel valve", "qty": 26, "price": "42.50" }
]

# params.json: one key per <parameter>
{ "CUSTOMER": "Distribuidora Caribe, S.A.", "ISSUED": "2026-03-05", "TAX_RATE": "0.18" }

The same render from code:

// JavaScript
import { render } from "ferroreport";
const pdf = render(jrxml, rows, params, { locale: "es_DO" });

# Python
import ferroreport
pdf = ferroreport.render("invoice.jrxml", rows, params, locale="es_DO")

# Any language, over HTTP
curl -X POST localhost:8080/render/invoice -H 'Content-Type: application/json' \
  -d '{"data": [...], "params": {...}, "locale": "es_DO"}' -o invoice.pdf

Template, data, parameters

Template

The JRXML source, exactly as Jaspersoft Studio saves it (JRXML 6 and the JRXML 7 element syntax). Compiled .jasper files are never loaded: if a template names lines.jasper, ferroreport reads lines.jrxml instead.

Data

A JSON array with one object per row, or one JSON object per line (JSON Lines). Keys match the <field name="..."> entries; a field named customer.name reads {"customer": {"name": ...}}. A missing key or null gives a null field. Each value is converted to the class the field declares:

Field classJSON you send
StringA string (other values are written as text)
Integer, Long, Double, FloatA number, or a numeric string
BigDecimalA number or a string. Use a string such as "185.00" to keep the exact digits
Booleantrue / false, or "true"
Date, Timestamp, TimeISO-8601 text ("2026-03-05", "2026-03-05T10:30:00", with or without offset) or epoch milliseconds
byte[] (images)Base64 text or a data: URI
List, CollectionA nested array, usually the rows of a subreport

Reports without a data source can omit the data. Templates with an embedded SQL query do not run it: send the rows.

Parameters

A JSON object with one key per <parameter>, converted with the same rules. Parameters you leave out take their defaultValueExpression.

Errors come back as {"error": "what went wrong"} with one of these statuses: 400 the request is malformed, 401 the token is missing or wrong, 404 the template does not exist, 411 the request has no Content-Length and asks to switch protocols, 413 the body is too large or the render went over the page or time limit, 429 the client asked too often (--rate-limit), 422 the template or its data cannot be rendered, 507 the document is too large for the memory and disk the server may use (--spool-memory, --spool-dir, --spool-disk).

A document is sent only once it is complete, with its Content-Length: the answer is the whole document or an error, never part of one. It comes with two more headers: Server-Timing (milliseconds spent parsing the template, 0 when it came from the cache, and rendering) and X-Report-Pages.

# curl
curl -X POST localhost:8080/render/invoice \
  -H 'Authorization: Bearer change-me' -H 'Content-Type: application/json' \
  -d '{"data": [{"sku": "FX-1000", "qty": 21, "price": "185.00"}], "params": {"CUSTOMER": "Caribe"}}' \
  -o invoice.pdf

# The same report as Excel
curl -X POST 'localhost:8080/render/invoice?format=xlsx' \
  -H 'Authorization: Bearer change-me' -H 'Content-Type: application/json' \
  -d '{"data": [...], "params": {...}}' -o invoice.xlsx
// Java: use the Java library, which talks to this server too
Ferroreport reports = Ferroreport.server(URI.create("http://localhost:8080"), "change-me");
byte[] pdf = reports.named("invoice").rows(lines).param("CUSTOMER", "Caribe").render();
// C#
using var http = new HttpClient();
http.DefaultRequestHeaders.Authorization = new("Bearer", "change-me");
var response = await http.PostAsJsonAsync("http://localhost:8080/render/invoice", new { data = rows, @params = parameters });
response.EnsureSuccessStatusCode();
byte[] pdf = await response.Content.ReadAsByteArrayAsync();
// PHP
$ch = curl_init("http://localhost:8080/render/invoice");
curl_setopt_array($ch, [
    CURLOPT_POSTFIELDS => json_encode(["data" => $rows, "params" => $params]),
    CURLOPT_HTTPHEADER => ["Content-Type: application/json", "Authorization: Bearer change-me"],
    CURLOPT_RETURNTRANSFER => true,
]);
$pdf = curl_exec($ch);

Large reports over HTTP

Two things can be changed, each on its own, for reports with more rows than you want in memory.

Rows one per line. Send Content-Type: application/x-ndjson with the request (everything in the table above except data) on the first line, and one row per line after it. The server reads the rows as the report asks for them, so neither side holds them all: a million rows render with the server at about 45 MB. Send them straight from a query:

# rows.ndjson
{"params": {"YEAR": 2026}}
{"sku": "FX-1000", "qty": 21, "price": "185.00"}
{"sku": "FX-2000", "qty": 4, "price": "92.50"}

curl -X POST localhost:8080/render/sales -H 'Authorization: Bearer change-me' \
  -H 'Content-Type: application/x-ndjson' -T rows.ndjson -o sales.pdf

# or without a file, as the database produces them
psql -At -c "select row_to_json(s) from sales s" | { echo '{"params": {"YEAR": 2026}}'; cat; } | \
  curl -X POST localhost:8080/render/sales -H 'Authorization: Bearer change-me' \
    -H 'Content-Type: application/x-ndjson' -T - -o sales.pdf

The first line may be as large as --max-body; the rows have no limit of their own (--timeout and --max-pages are what stop a report that is too large).

The document as it renders. By default the server keeps the document until it is complete (in memory up to --spool-memory, then in a file), so that an error is always an error and never half a PDF. Add Prefer: respond-streaming and the document is sent while it renders instead: the first bytes arrive in a fraction of a second, however long the report is, and nothing is kept on the server. The answer says so with Preference-Applied: respond-streaming.

DefaultPrefer: respond-streaming
First byteWhen the report is finishedAt once
An error while renderingAn error status and {"error": ...}; no documentBefore the first 64 KB: the same. After that the status is already 200, so the response is cut short in a way every HTTP client reports as an error (curl exits with 56, Java throws IOException, Python raises IncompleteRead). Never keep a file whose download failed
The client goes awayThe render runs to its end or to --timeoutThe render stops within milliseconds
HeadersContent-Length, X-Report-Pages, Server-TimingTransfer-Encoding: chunked
Server memory and diskThe document, up to --spool-memory; the rest on diskNone for the document. Rows sent one per line are put aside first (a request cannot be read while it is being answered)

Both give the same bytes. Use the default unless you need the first bytes early (a browser download of a long report, a gateway with a short time-out) or want abandoned downloads to stop costing work. In Docker the files go to /tmp, which the image provides; with a read-only root filesystem, mount a volume there or set FERROREPORT_SPOOL_DIR. Without a place to write, documents over --spool-memory are answered with 507.

These promises are checked on every change by tools/http_check.py: a million rows, 50 clients at once, a client that leaves half way, a wrong row in each mode, and the same bytes as the command line for every test report.

JavaScript

For Node.js 18+, Deno, Bun and browsers. The engine is WebAssembly: no native build step, no JVM.

import { render, inspect, version } from "ferroreport";
import { readFileSync, writeFileSync } from "node:fs";

const pdf = render(
  readFileSync("invoice.jrxml", "utf8"),      // template: the JRXML text
  rows,                                        // data: array of objects, or JSON text
  { CUSTOMER: "Distribuidora Caribe" },        // params: object, or JSON text
  {
    locale: "es_DO",
    now: new Date("2026-03-05T10:00:00"),      // optional: value of new Date() in expressions
    resources: {                               // optional: images and subreports, by the path the template uses
      "logo.png": readFileSync("logo.png"),
      "lines.jrxml": readFileSync("lines.jrxml", "utf8"),
    },
  },
);
writeFileSync("invoice.pdf", pdf);             // pdf is a Uint8Array

// Excel or CSV: the same call with options.format
writeFileSync("invoice.xlsx", render(template, rows, params, { format: "xlsx" }));
FunctionReturns
render(template, data?, params?, options?)Uint8Array with the PDF (or the Excel workbook or CSV text with options.format). Throws an Error with the reason if the template cannot be rendered
inspect(template){ name, parameters, fields, warnings }. warnings lists what the engine does not support in that template
version()The engine version

options holds locale, now, resources (as above) and format: "pdf" (default), "xlsx" or "csv" (UTF-8 bytes). Also maxPages (stop a report that grows past that many pages), csvSafe (guard CSV against spreadsheet formulas in the data) and xlsxNumbers (numbers as numbers in Excel).

In a browser, or with a bundler that picks the web build, load the engine once before the first render:

import init, { render } from "ferroreport";
await init();
const pdf = render(template, rows, params);
window.open(URL.createObjectURL(new Blob([pdf], { type: "application/pdf" })));
// Express: send a PDF
app.get("/invoices/:id.pdf", async (req, res) => {
  const { rows, params } = await loadInvoice(req.params.id);
  res.type("application/pdf").send(Buffer.from(render(template, rows, params, { locale: "es_DO" })));
});

Templates read files only from options.resources, so the JavaScript build never touches the disk on its own.

Images, subreports and style templates

A template refers to other files by relative path: "logo.png" in an image expression, "lines.jasper" in a subreport expression. ferroreport looks for them in the template's folder, then in the resource folders you add, then among the resources you pass in memory. A path can never leave those folders, and remote URLs are not fetched.

Images are PNG, JPEG or GIF (its first picture, with its transparent color). They can also come from the data: a byte[] field with base64 content, or a string field with a base64 expression.

A subreport gets its rows from a nested array in the parent row:

# Parent row
{ "order": "ORD-2026000", "customer": "Grupo Ramos",
  "lines": [ { "product": "Clavos 3\"", "qty": 26, "price": 65.0 }, ... ] }

# In the parent template: a field of class java.util.List, and
<dataSourceExpression><![CDATA[new JRMapCollectionDataSource($F{lines})]]></dataSourceExpression>
<subreportExpression><![CDATA["lines.jasper"]]></subreportExpression>    # read from lines.jrxml

JRBeanCollectionDataSource, ((JsonDataSource)$P{REPORT_DATA_SOURCE}).subDataSource("lines") and JREmptyDataSource work the same way. Subreport parameters and return values are supported.

Style templates are found the same way: <template><![CDATA["styles.jrtx"]]></template> reads styles.jrtx from the template's folder, a resource folder or the resources in memory (over HTTP, the resources of the request). A .jrtx that includes another is read with it, the included one looked for next to it first. Styles are taken in JasperReports' order: those of each template after the templates it includes, then the report's own; a style defined again replaces the earlier one for what comes after it. The location can be a string or a parameter whose default is one. In Rust, parse with Renderer::parse instead of ferroreport::parse, which does not read files.

Tables

Tables (jr:table) work as they do in JasperReports: the table iterates over a <subDataset> whose rows come from the dataSourceExpression of its datasetRun, usually a nested array of the current row, and its datasetParameters pass values in. Fields of the main report are not visible inside the table; pass them as parameters.

<subDataset name="lines">
  <parameter name="ORDER" class="java.lang.String"/>
  <field name="product" class="java.lang.String"/> ...
</subDataset>
...
<jr:table>
  <datasetRun subDataset="lines">
    <datasetParameter name="ORDER"><datasetParameterExpression><![CDATA[$F{order}]]></datasetParameterExpression></datasetParameter>
    <dataSourceExpression><![CDATA[new JRMapCollectionDataSource($F{lines})]]></dataSourceExpression>
  </datasetRun>
  <jr:column width="235"> ... </jr:column>
</jr:table>

Supported: columns and nested column groups, table header and footer, column headers (printed again on every page the table continues on), column footers, detail cells, group header and footer cells for the subdataset's groups, printWhenExpression on columns, the no-data cell (whenNoDataType="NoDataCell") and subdataset variables. The SQL query of a subdataset is not run: the rows come from the data source expression.

Lists (jr:list) use the same datasetRun: the list contents are repeated for each row, one below the other, and continue on the next page when they do not fit.

Crosstabs

Crosstabs made in Jaspersoft Studio render as they do in JasperReports. The rows come from the report itself (place the crosstab in the summary band) or from a subdataset through its datasetRun, for example one crosstab per detail row over a nested JSON array.

  • Row and column groups sort their bucket values ascending or descending, and print their totals at the start, the end or not at all. Group headers sit at the start, middle or end of the cells they span (headerPosition).
  • Measures can be Sum, Count, DistinctCount, Average, Highest, Lowest, First or Nothing. In a cell, $V{measure} is the value of that cell, $V{measure_group_ALL} the total of a group, $V{measure_rowGroup_columnGroup_ALL} the total of both, and $V{group} the bucket value. Cells without data show zero for sums and counts. Totals add up the totals of the buckets below them, as Jasper does, so decimals round the same way.
  • A crosstab wider than its element is cut into column parts, printed one below the other (columnBreakOffset apart) with the row headers repeated. One taller than the page continues on the next page with the column headers repeated (repeatColumnHeaders, repeatRowHeaders).
  • <crosstabParameter> values are evaluated in the report and read with $P{} inside the crosstab.
  • percentageOf="GrandTotal" shows a measure as a percentage of the grand total (100 × value / total, in the measure's class: whole numbers divide as integers, BigDecimal rounds half up).
  • orderByExpression sorts a group's buckets by a value computed on each bucket's totals, for example $V{amountMeasure} to list regions by their sales; ties keep the natural order.

Not yet: bucket comparators (comparatorExpression), and crosstabs over the rows of a group only (they use all the rows read so far). ferroreport doctor warns about these.

Excel and CSV

A template that renders to PDF also exports to an Excel workbook (.xlsx) or a CSV file. Both follow JasperReports' own exporters with their default settings, so the spreadsheet comes out the way it did with Jasper: every fixture in the test suite gives the same worksheet, styles and CSV text as JasperReports 6.20, byte for byte.

Excel

  • All pages go on one sheet named after the report, one below the other, page margins included.
  • The edges of the elements cut each page into columns and rows. A column is as wide as the gap between two cuts (in Excel units of 6 points) and a row as tall as its gap, in points.
  • Each text sits in the cells it covers, merged, with its font, size, bold, italic, underline, color, background, borders and alignment. Rotated text is rotated in the cell. Styled and HTML text keeps its formatting run by run.
  • A text that does not fit its box is cut the same way as in the PDF.
  • Lines become the border of the cells they lie on, rectangles fill and outline their cells, and frames give their background and borders to the cells inside them.
  • Images sit over their cells with the same scale mode (RetainShape, FillFrame, Clip) and alignment. Charts and barcodes are drawn as pictures at twice Jasper's resolution, so they stay sharp.
  • Where two elements overlap, the one on top wins, as in Jasper; the other is left out.
  • Values are written as the text you see in the PDF (3,885.00), like Jasper. With --xlsx-numbers on the command line, or XlsxOptions { detect_cell_type: true } in Rust, numbers are written as numbers with their format pattern, so the spreadsheet can add them up.

CSV

Only texts are exported. Every line of a page where a text starts becomes a row, and every column where a text starts on that page becomes a field. Fields holding a comma, a quote or a line break are quoted; quotes are doubled. Pages follow one another.

A value that starts with =, +, - or @ can be run as a formula by the spreadsheet that opens the CSV. When the data comes from other people, turn on the guard (--csv-safe, csv_safe=True, csvSafe: true): those values get an apostrophe in front, which spreadsheets show as text. Numbers such as -12.50 are left alone. It is off by default so the CSV stays exactly what JasperReports writes.

Not available yet: other exporters (Word, HTML, ODS, the old XLS format) and the net.sf.jasperreports.export.* properties other than number detection.

Accessible PDFs

A PDF is a picture of pages unless it also says what is on them. With tagging on, the document carries that description (a tagged PDF): each text element is a paragraph and each image, chart and barcode a figure, in reading order; tables and crosstabs are tables, with their rows, their data cells and their header cells, each header saying whether it names a column or a row; lines, borders and backgrounds are marked as decoration, so a screen reader skips them; and the document has its title and the language of the locale. The pages look exactly the same.

Lists are tagged as paragraphs, and a cell that spans several columns or rows does not say so. The files do not claim PDF/UA conformance: that needs a validator's verdict, which this project will publish when it has one. A tagged PDF is larger (an entry per text) and a value known only later, such as "page 3 of 240", makes its page wait instead of being added afterwards.

HTML previews

Ask for html (-o report.html, format="html", Format::Html, Format.HTML) and you get one web page with every page of the report drawn as it is in the PDF: same positions, fonts, colors, images, charts and barcodes. The text is real text, so it can be selected, searched and read aloud, and everything from the template or the data is escaped. The page has no scripts and loads nothing from the network.

Each line of text carries its measured width, so the layout holds even where the browser does not have the report's font and falls back to another. Use it to show a report in a browser without a PDF viewer; the PDF remains the document to print or keep. In Rust, HtmlOptions { fragment: true, .. } gives only the pages, to place inside a page of your own.

Large reports and limits

A report does not have to fit in memory. Rows are read as the report asks for them and each page is written as soon as it is finished, so a million rows and 23,810 pages render in about 11 MB, at about 85,000 rows a second on one core.

FromHow
Command lineNothing to do: ferroreport render sales.jrxml -d sales.json -o sales.pdf already reads and writes as it goes. The rows can be a JSON array or one object per line, from a file or from standard input

JavaScriptRows arrive in the call, so they are in memory; the document is still built page by page

What this covers, and what it does not:

  • PDF and CSV are written page by page. So are Excel workbooks, in two passes: the columns of a sheet come from every page, so a large report is filled once to find them and once more to write its rows, which are compressed and sent on as they are made (100,000 rows: about 3 s and 58 MiB; 500,000: 17 s and 92 MiB). That needs rows that can be read twice: a file, or rows the command line, the server, Python and Java put aside for you; in Rust, render_rows_to. Small workbooks are still filled once. A report with more rows than a sheet holds (1,048,576) stops with an error that says so.
  • Values known only later, such as "page 3 of 240", a grand total in the title or a group total in the group header, are added to their page when they are known, without holding the page back. If something is drawn over such a value, its page waits for it instead, so the result is always the same document.
  • A crosstab over the report's own rows needs them all, so those rows are kept until the crosstab prints. Crosstabs, tables, lists and subreports over nested data are not affected.

Two limits stop a report that grows past what you expect. Set them whenever templates or data come from other people:

Rows from a database

The engine does not open database connections: your application already has one, with its credentials and its pool. Hand it the rows as they come and nothing is held in memory. Templates with an embedded SQL query do not run it.

# PostgreSQL: one JSON object per row, straight into the report
psql -At -c "select row_to_json(s) from (select * from sales order by region) s" mydb \
  | ferroreport render sales.jrxml -d - -o sales.pdf

# SQLite, MySQL
sqlite3 -json app.db "select * from sales order by region" | ferroreport render sales.jrxml -d - -o sales.pdf
mysql -N -B -e "select json_object('region', region, 'amount', amount) from sales" mydb \
  | ferroreport render sales.jrxml -d - -o sales.pdf
// Java: the ResultSet is read as the report needs it
reports.template(Path.of("sales.jrxml")).rows(statement.executeQuery("select * from sales")).renderTo(Path.of("sales.pdf"));
# Python: any cursor or generator is read one row at a time
cursor.execute("select region, amount from sales order by region")
rows = (dict(zip(("region", "amount"), r)) for r in cursor)
ferroreport.render_to_file("sales.jrxml", "sales.pdf", rows)

Fonts

DejaVu Sans, DejaVu Serif and DejaVu Sans Mono are built in. They are the families of the jasperreports-fonts extension, so templates that use them match JasperReports exactly. A family the engine does not have is replaced by a built-in one.

Add your own TrueType or OpenType fonts with --font on the command line or register_font in Rust. The JavaScript and Python packages use the built-in families for now.

Locale and dates

The locale decides how patterns such as #,##0.00 and dd MMMM yyyy are written: decimal and grouping separators, month and day names. Supported: en_US, es_DO, es_MX, es_ES.

Dates are kept as written, without time zone conversion. new Date() in an expression is the current time, unless you fix it with now, which makes the output byte-for-byte reproducible.

Check a template

Before you depend on a template, ask the engine what it thinks of it:

$ ferroreport doctor invoice.jrxml
invoice.jrxml: report `invoice`
  page 595x842 pt, margins 30/40/30/40, language Java
  5 parameters, 5 fields, 3 variables, 0 groups
  elements: line ×1, rectangle ×1, staticText ×9, textField ×17
✓ every feature used by this template is supported

From code, inspect(template) (JavaScript, Python) and POST /inspect return the same verdict as data: an empty warnings list means every feature in the template is supported.

Errors

A render either returns a complete PDF or fails with a message that names the cause. The usual ones:

MessageWhat to do
invalid report templateThe text is not JRXML. Send the .jrxml source, not a compiled .jasper file
cannot convert ... to ...A value does not fit the class its field declares. See the table in Data
An expression errorThe expression uses a Java class or method outside the supported subset. doctor points at it
An image or subreport is not foundAdd its folder as a resource directory, or pass the file in resources

Templates cannot run code, read files outside the resource folders or open network connections, so it is safe to render templates your users upload.

What is supported

Bands and page breaks, groups and variables, frames, images, subreports, tables (jr:table), lists (jr:list), crosstabs, charts, barcodes (QR, Code 128, Code 39, EAN-13, EAN-8, UPC-A, Interleaved 2 of 5, Codabar), styled and HTML text, rotation, multi-column layouts in either print order, conditional styles and style templates, exported to PDF, Excel, CSV or HTML. The compatibility table in the repository lists every feature and what is not there yet, and ferroreport doctor gives the answer for your own template.
